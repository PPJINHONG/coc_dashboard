# 상대가 파일을 옮겼는데 내 코드와 충돌했어요

[문서 목록](../README.md) · [작업 중 최신 코드 가져오기](git-scenarios.md)

**상대가 폴더·파일 위치와 내용을 바꿨고, 나는 예전 파일에서 개발하던 상황**을 예로 설명합니다. 아래 파일 이름은 설명용이며 실제 프로젝트에 있다는 뜻은 아닙니다.

이 문서는 내 작업을 먼저 커밋한 뒤, **내 기능 브랜치에서 `git merge origin/main`을 실행하다 멈춘 경우**를 기준으로 합니다. 다른 명령에서 생긴 오류는 처리 방법이 다를 수 있습니다.

## 먼저, Fetch와 Merge 구분하기

| 실행한 명령 | 하는 일 |
| --- | --- |
| `git fetch origin` | 최신 기록을 받기만 함. 내 파일 내용은 그대로 |
| `git merge origin/main` | 받은 공용 코드를 내 작업과 합침. 여기서 파일 충돌 가능 |

`fetch`를 말한 것이라면 그것만으로 내 파일을 합치다가 충돌하지는 않습니다. 뒤이어 실행한 Merge나 Pull 등에서 어떤 메시지가 나왔는지 구분합니다. [Fetch 공식 설명](https://git-scm.com/docs/git-fetch)

## 1. 목표를 파일 하나로 생각해 보기

두 사람 모두 처음에는 같은 보고서 화면에서 출발했다고 가정합니다.

| 구분 | 파일 위치 | 들어 있는 기능 |
| --- | --- | --- |
| 처음 공용 코드 | `frontend/src/Report.tsx` | 보고서 조회 |
| 내가 개발하던 코드 | 같은 옛 위치 | 보고서 조회 + 내가 추가한 엑셀 다운로드 |
| 상대가 main에 합친 코드 | `frontend/src/pages/ReportPage.tsx`로 이동 | 보고서 조회 + 상대가 추가한 날짜 필터 |

Git이 이동을 알아내지 못하거나 같은 부분의 내용을 합치지 못하면 충돌이 날 수 있습니다. 이때 Git이 묻는 것은 다음과 같습니다.

> “너는 옛 파일을 고쳤고, 상대는 그 파일을 옮기고 내용도 바꿨어. 최종 파일을 어떻게 만들어야 할까?”

두 사람이 **상대의 새 구조를 사용하기로 했다면** 목표는 이렇습니다.

```text
최종 위치: frontend/src/pages/ReportPage.tsx
남길 기능: 보고서 조회 + 날짜 필터 + 엑셀 다운로드
옛 위치: 필요한 기능을 모두 옮겼다면 제거
```

**새 위치에서 두 사람의 기능이 함께 작동하도록 고치는 작업**입니다. 내용을 모르고 버튼이나 명령 하나로 항상 끝낼 수 있는 단계는 아닙니다.

## 2. 어떤 파일이 문제인지 확인

현재 기능 브랜치에 그대로 있는 상태에서 실행합니다. Merge를 다시 실행하지 않습니다.

```bash
git status
git diff --name-only --diff-filter=U
```

두 번째 명령은 아직 해결하지 않은 파일 이름을 보여줍니다. `git status`에서는 다음 표현이 나올 수 있습니다. 이 문서의 Merge 상황 기준입니다.

| 표시 | 쉬운 뜻 |
| --- | --- |
| `both modified` | 나와 상대가 같은 파일을 수정함 |
| `deleted by them` | 상대 main에서는 그 위치의 파일이 없어졌고, 나는 수정함. 다른 곳으로 옮겼을 수도 있음 |
| `deleted by us` | 내 브랜치에서는 그 위치의 파일이 없어졌고, 상대는 수정함 |

“삭제”라고 나와도 기능을 없앤 것인지 다른 곳으로 옮긴 것인지 먼저 확인합니다. [상태 표시 공식 설명](https://git-scm.com/docs/git-status)

## 3. 새 위치에 내 기능 옮기기

위 보고서 예시라면 다음 순서입니다. 실제로는 상태 목록과 상대 PR에 나온 경로를 사용합니다.

1. 상대에게 “예전 보고서 파일을 어디로 옮겼어?”라고 확인하거나, 상대 PR의 **Files changed**에서 새 위치를 찾습니다.
2. 새 파일 `pages/ReportPage.tsx`를 봅니다. 상대의 날짜 필터가 있는지, 내 엑셀 기능이 이미 자동으로 합쳐졌는지 확인합니다.
3. 엑셀 기능이 빠졌다면 **그 기능에 필요한 부분을 새 파일 구조에 맞춰 추가**합니다. 옛 파일 전체를 새 파일에 덮어쓰지 않습니다.
4. 관련 파일도 맞춥니다. 파일을 불러오는 `import`, API 주소, Docker 경로가 바뀌었다면 함께 수정합니다.
5. 옛 파일을 사용하던 코드가 있다면 새 위치를 사용하도록 고칩니다.
6. 기능을 모두 옮겼고 옛 파일을 더는 사용하지 않는다고 확인한 뒤, 남아 있는 옛 파일을 편집기에서 삭제합니다. 이미 없어졌다면 다시 삭제할 필요는 없습니다.

Git이 이동을 알아봤다면 옛 파일은 없고 **새 위치의 파일 안에서 충돌**이 날 수도 있습니다. 그때는 새 파일에서 내용을 해결합니다. 무조건 옛 파일을 다시 만들지 않습니다.

내가 커밋한 옛 내용이 작업 폴더에서 안 보이면 기록에서 볼 수 있습니다. 다음은 **위 예시 경로일 때만 쓰는 명령**입니다. 실제 경로로 바꿔야 합니다.

```bash
git show HEAD:frontend/src/Report.tsx
```

Merge가 진행 중일 때 `HEAD`는 병합 직전 내 브랜치의 커밋입니다. 위 명령은 그 커밋의 파일을 보여주며 덮어쓰지 않습니다. 긴 화면에서 나오려면 `q`를 누릅니다. 커밋하지 않았던 내용까지 찾아주는 명령은 아닙니다.

## 4. 코드 안에 구분 표시가 있다면

```text
  <<<<<<< HEAD
  내 쪽에서 고친 부분
  =======
  가져온 main 쪽에서 고친 부분
  >>>>>>> origin/main
```

이 Merge에서는 위가 내 코드, 아래가 가져온 코드입니다. 예시의 목표처럼 두 기능을 살리는 최종 코드로 고친 다음 구분 표시 줄을 지우고 저장합니다. 이동·삭제 충돌에는 이런 표시가 없을 수도 있습니다.

**Accept Current**는 내 쪽, **Accept Incoming**은 가져온 쪽을 선택하는 버튼입니다. 한쪽만 고르면 다른 쪽 기능이 빠질 수 있습니다. 내용을 읽기 어렵다면 다음처럼 AI에게 파일 수정을 맡길 수 있습니다.

## 5. AI에게 맡길 때 복사할 요청문

자기 기능과 합의한 구조 부분을 바꿔 사용합니다. 내 코드가 미완성이면 지금까지 만든 동작도 적습니다.

```text
내 기능 브랜치에서 git merge origin/main을 실행하다 충돌이 났어.
병합 전 내 작업은 커밋해 둔 상태야.

상대는 main에 폴더·파일 위치와 내용을 바꿨고,
나는 옛 위치에서 엑셀 다운로드 기능을 만들고 있었어.
두 사람이 사용할 최종 구조는 최신 main의 새 폴더 구조야.

1. git status와 충돌 목록을 읽고 옛 파일이 새 구조의 어디에 대응하는지 알려줘.
2. 병합 전 내 커밋(HEAD)과 origin/main을 비교해 양쪽 변경을 확인해 줘.
3. 상대의 새 구조와 기능을 유지하면서 내 엑셀 기능을 새 위치에 맞게 옮겨 줘.
4. 관련 import, API 주소, Docker 경로도 필요한 경우 맞춰 줘.
5. 옛 파일을 지워도 되는 근거와 내가 실행해서 확인할 항목을 설명해 줘.
6. 파일 수정까지만 해 줘. Git add·commit·push·reset·abort는 내가 직접 할게.

합칠 의도나 옮길 위치가 불분명한 부분은 임의로 버리지 말고 질문해 줘.
```

## 6. 수정이 끝나면 Git에 해결 결과 기록

위 예시처럼 옛 파일과 새 파일이 모두 `frontend/src` 아래라면 다음으로 **그 폴더의 수정·추가·삭제 결과**를 준비합니다. 다른 폴더라면 실제 해당 폴더 경로로 바꿉니다.

```bash
git add -A -- frontend/src
git diff --name-only --diff-filter=U
git diff --cached
git status
```

옛 파일 삭제도 기록해야 하므로 새 파일만 Add하고 끝내지 않습니다. 다른 폴더에도 충돌이 있다면 그 파일들도 해결해 준비합니다.

미해결 목록이 비어 있고, `git status`에 모든 충돌을 해결했지만 아직 병합 중이라는 안내가 나오는지 봅니다. 커밋 목록에 의도한 최종 내용이 들어 있는지도 확인합니다.

설정을 확인하고 다시 실행합니다. 내 기능이 미완성이면 현재까지 구현한 부분과 상대 기능을 확인합니다.

```bash
docker compose config --quiet
docker compose up --build -d
```

예시에서는 날짜 필터와 엑셀 다운로드를 각각 눌러 보고 함께 작동하는지 확인합니다. 추가로 파일을 고쳤다면 해당 파일을 다시 Add하고 확인합니다. 그다음 병합 기록을 만듭니다.

```bash
git commit -m "merge: 새 구조에 내 기능 반영"
```

이후 자기 브랜치에 Push하고 계속 개발하거나 기존 PR을 갱신합니다. 최종 main 병합은 완성·검사·상대 검토를 마친 뒤 진행합니다.

## 아직 해결하기 어렵다면 이번 Merge 중단

병합 전 내 작업을 커밋해 두었고 지금 Merge가 충돌로 멈춘 상태라면 다음으로 병합 전 상태로 돌아가려 할 수 있습니다. **충돌 해결 중 새로 수정한 내용은 유지되지 않을 수 있으므로** 따로 필요한 내용이 있는지 먼저 확인합니다.

```bash
git merge --abort
git status
```

이미 끝난 병합, Rebase, Stash 복원 오류에 그대로 쓰는 명령은 아닙니다. 어떤 상태인지 모르면 먼저 `git status`로 확인합니다. [Merge 공식 설명](https://git-scm.com/docs/git-merge)

해결책을 모르는 상태에서 `reset --hard`, `clean -fd`, 강제 Push로 넘기지 않습니다.
