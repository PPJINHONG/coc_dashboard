# 상대방 코드가 바뀌었을 때 어떻게 하나요?

[문서 목록](../README.md) · [평소 Git 순서](git_collaboration_guide.md)

**내가 개발하는 사이 상대 PR이 합쳐졌거나, 두 사람 모두 큰 변경을 만든 경우**에 읽습니다.

## 상황 1. 상대 PR이 합쳐졌는데 나는 아직 개발 중이에요

**내 작업을 다 끝낼 때까지 기다릴 필요가 없습니다.** 지금 브랜치에 최신 공용 코드를 합쳐서 계속 개발할 수 있습니다.

아래에서는 내 브랜치를 `feature/report-ui`라고 부릅니다. 명령의 이름은 실제 자기 브랜치로 바꿉니다. 오류가 나면 다음 명령을 실행하지 않습니다.

### 1단계. 상대 PR이 실제로 합쳐졌는지 확인

GitHub에서 상대 PR 상태가 **Merged**인지 봅니다. **Approved**는 승인했다는 뜻이므로 아직 공용 코드에 없을 수 있습니다. 자동 병합을 따로 설정한 경우도 최종 상태로 판단합니다.

### 2단계. 내 작업을 중간 저장

현재 내 브랜치가 맞는지 확인합니다.

```bash
git branch --show-current
git status
```

다른 브랜치라면 미커밋 파일이 어디에 속하는지 먼저 확인합니다. 그대로 브랜치를 바꾸면 변경이 따라갈 수 있습니다.

내 브랜치에서 아직 커밋하지 않은 변경이 있다면 실행합니다.

```bash
git add .
git diff --cached
git commit -m "wip: 최신 공용 코드를 받기 전 중간 저장"
git status
```

내용을 확인하고 커밋합니다. 마지막 결과가 `working tree clean`인지 봅니다. 이미 변경을 모두 커밋했다면 커밋 단계는 생략합니다. 미완성 기능도 중간 저장할 수 있습니다.

GitHub에도 보관해 두고 싶다면 먼저 `git push -u origin feature/report-ui`를 실행해도 됩니다. 업로드만으로 main에 합쳐지지 않습니다.

### 3단계. 내 브랜치에서 최신 main 가져오기

**main으로 이동하지 않고 내 작업 브랜치에 그대로 있는 상태에서** 실행합니다.

```bash
git fetch origin
git merge origin/main -m "merge: 최신 main 반영"
```

| 명령 | 쉬운 뜻 |
| --- | --- |
| `git fetch origin` | GitHub의 최신 기록 위치를 받아 확인 |
| `git merge origin/main` | 받아 확인한 공용 코드를 지금 내 브랜치에 합치기 |

Fetch만으로 내 파일을 합치지는 않습니다. 파일 충돌이 생겼다면 보통 그다음 Merge처럼 실제로 합치는 단계에서 생긴 것입니다.

내 PC의 main을 먼저 바꿀 필요는 없습니다. [Git 공식 설명](https://git-scm.com/docs/git-merge)

| 나온 결과 | 다음 행동 |
| --- | --- |
| 병합 성공 | 내 코드와 상대 코드가 함께 있는 상태에서 계속 진행 |
| `Already up to date.` | 이미 받아 반영한 공용 기록이므로 다음 단계 진행 |
| `CONFLICT` | 자동으로 못 합친 부분이 있음. [충돌 해결](git-conflicts.md)부터 진행 |

**상대가 폴더와 파일 위치까지 바꿔서 충돌했다면:** 두 사람이 새 구조를 사용하기로 했는지 먼저 확인합니다. 예를 들어 상대는 보고서 파일을 새 폴더로 옮기고 날짜 필터를 추가했고, 나는 옛 파일에 엑셀 기능을 추가했다면 **새 폴더의 보고서에 날짜 필터와 엑셀 기능이 함께 있도록** 고칩니다.

이때는 내 파일이나 상대 파일 중 하나를 통째로 고르는 대신 기능을 새 구조에 맞추는 코드 수정이 필요할 수 있습니다. [파일 이동 충돌의 예시와 AI에게 맡기는 요청문](git-conflicts.md)을 따라 한 파일씩 해결한 뒤 4단계로 돌아옵니다.

### 4단계. 새 구조에서 내 기능 확인

파일 위치나 API 주소가 바뀌었다면 내 코드도 그에 맞게 고칩니다. 프로젝트 최상위에서 설정을 확인하고 다시 실행합니다.

```bash
docker compose config --quiet
docker compose up --build -d
```

오류 없이 끝나면 브라우저에서 내 기능과 상대 기능을 모두 확인합니다. [변경별 확인할 내용](#상황-3-파일dockerapi-구조가-바뀌었어요)도 참고하세요.

추가 수정이 있다면 `git add .`로 준비하고 내용을 확인한 뒤 커밋합니다. 수정이 없다면 추가 커밋은 필요 없습니다.

```bash
git add .
git diff --cached
git commit -m "fix: 바뀐 공용 구조에 화면 맞추기"
```

### 5단계. 같은 브랜치에 올리고 계속 개발

```bash
git push -u origin feature/report-ui
```

미완성이면 같은 브랜치에서 계속 개발합니다. PR이 있다면 갱신되며, 없다면 완성 후 만들거나 Draft로 먼저 공유합니다. 최종 PR을 합치기 전에는 최신 검사와 필요한 재승인을 확인합니다.

## 상황 2. 둘 다 많은 파일을 바꿨어요. 누가 먼저 올리나요?

**자기 브랜치에 커밋하고 올리는 순서는 자유입니다. 공용 main에 합칠 순서를 정해야 합니다.**

예를 들어 A가 폴더와 Docker 구성을 바꾸고, B가 화면을 개발했다면 다음처럼 진행합니다.

1. 각자 자기 브랜치에 작업을 커밋하고 올립니다. 미완성이면 Draft PR로 공유합니다.
2. PR의 **Files changed**를 같이 보고 겹치는 파일과 변경 목적을 확인합니다.
3. B가 쓸 공통 구조를 A가 바꿨다면 A의 PR을 먼저 검토하고 합칩니다.
4. B는 위의 상황 1처럼 **자기 브랜치에 최신 main을 합칩니다**.
5. B가 새 구조에 맞추고 실행 확인 후 올립니다.
6. A가 B의 최종 변경을 검토하고 B의 PR도 합칩니다.

| 두 작업의 관계 | 먼저 합칠 변경 |
| --- | --- |
| 화면에서 새 API를 사용해야 함 | 필요한 API를 제공하는 변경 |
| 기능에서 새 폴더·공통 코드를 사용해야 함 | 그 기반을 제공하는 변경 |
| 서로 관계없는 작업 | 준비된 PR부터. 다음 PR은 최신 main으로 다시 확인 |
| 어느 쪽도 혼자서는 실행이 안 됨 | 공통 기반을 따로 작게 나눠 먼저 합칠 수 있게 조정 |

먼저 합치는 PR만으로도 기존 기능이 동작해야 합니다. 폴더를 옮겼다면 Docker 경로와 코드에서 파일을 불러오는 경로도 함께 맞춰야 합니다.

## 상황 3. 파일·Docker·API 구조가 바뀌었어요

Git이 합치는 것은 파일 변경입니다. `.env`, 실행 중인 프로그램, 내 DB 데이터까지 자동으로 맞춰주지는 않습니다.

| 바뀐 것 | 내가 확인할 것 |
| --- | --- |
| 폴더·파일 위치 | 그 파일을 불러오는 코드, Dockerfile의 COPY 경로, Compose의 build 경로 |
| Docker 구성 | 새 구성이 빌드되고 실행되는지, 접속 주소가 달라졌는지 |
| 환경변수 | 양식의 새 항목을 내 기존 `.env`에도 넣었는지. 덮어쓰지는 않기 |
| API | 주소·요청·응답 형식에 맞게 내 호출 코드도 바꿨는지 |
| 사용 프로그램 | package 파일과 설치 버전 기록이 맞는지, 새 이미지가 만들어지는지 |
| DB 표 구조 | 기존 DB에 적용할 방법과 순서를 두 사람이 정했는지 |

관련 안내: [설정](../02-development/configuration.md), [실행](../02-development/docker-compose.md), [API](../02-development/api.md), [DB](../02-development/database.md).

## 충돌 메시지가 없으면 정상인가요?

자동으로 파일이 합쳐져도 기능은 깨질 수 있습니다. 예를 들어 A가 서버 주소를 바꾸고 B는 다른 파일에서 예전 주소를 쓰면, Git은 충돌을 표시하지 않아도 데이터 요청은 실패합니다.

오래된 main에서 출발했다고 상대 파일을 통째로 옛날 것으로 덮어쓰는 것은 아닙니다. 다만 내가 실제로 수정·삭제·되돌린 부분은 결과에 영향을 줍니다. **병합 성공 후에도 빌드와 실제 동작을 확인합니다.**

## 이런 상황을 줄이려면

- 작업 전에 바꿀 폴더, 공통 설정, API를 상대에게 알려줍니다.
- 공통 기반을 추가하고, 사용하는 기능을 옮긴 뒤, 예전 구조를 제거하는 순서로 나눕니다.
- 상대가 큰 구조 변경을 합쳤다면 내 브랜치에도 일찍 반영합니다.
- AI에게 작업 범위를 알려주고 끝난 뒤 `git diff --stat`과 `git diff`로 예상 밖 파일 변경을 확인합니다.
- 담당 기능, API 변경 순서, DB 변경 방법은 두 사람이 먼저 합의합니다. 아직 정해진 것으로 취급하지 않습니다.

공유 예시: “나는 화면 폴더를 옮기고 Docker 경로도 바꿀게. 이 PR을 먼저 합친 뒤 네 화면 브랜치에 main을 반영하자.”
