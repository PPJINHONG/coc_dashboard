# 개발 문서의 말을 쉽게 풀어보기

[문서 목록으로 돌아가기](../README.md)

외울 필요 없이, 다른 문서를 읽다가 모르는 말이 나오면 찾아보세요. 명령어와 파일 이름은 실제로 입력해야 하므로 영어 그대로 사용합니다.

## 파일과 실행에 나오는 말

| 단어 | 쉬운 뜻 | 이 프로젝트의 예 |
| --- | --- | --- |
| 프로젝트 루트 | 프로젝트의 가장 바깥 폴더 | `compose.yaml`이 있는 `coc_dashboard/` |
| 터미널 | 명령어를 글자로 입력하는 창 | VS Code의 Terminal |
| 로컬 | 내 컴퓨터 | 내 PC에서 실행한 화면 |
| 프론트엔드 | 사용자가 보는 화면 부분 | `frontend/` |
| 백엔드 | 화면 뒤에서 요청을 처리하는 서버 부분 | `backend/` |
| DB, 데이터베이스 | 데이터를 저장하고 찾는 보관소 | PostgreSQL |
| 테이블 / 행 / 열 | 데이터 표 / 한 건 / 항목 | `test` 표의 `id`, `message` |
| API | 프로그램이 데이터나 작업을 요청하는 창구 | `/api/test/`에 조회 요청 |
| 요청 / 응답 | 보내는 질문 / 돌아오는 결과 | 데이터 달라고 요청 → 목록 응답 |
| GET | 데이터를 읽어 달라는 요청 방식 | 현재 조회 API에서 사용 |
| JSON | 항목 이름과 값을 짝지어 적는 데이터 형식 | `{"message": "Hello"}` |
| SQL | DB에 조회·생성 등을 요청하는 언어 | `SELECT`로 데이터 읽기 |
| 포트 | 같은 컴퓨터에서 접속 대상을 구분하는 번호 | `localhost:8080`의 `8080` |
| 환경변수 | 코드 밖에서 정해 주는 설정값 | DB 이름, 비밀번호 |
| 패키지 / 의존성 | 프로젝트가 가져다 쓰는 다른 프로그램 | React, Django |
| 빌드 | 코드를 실행할 수 있는 형태로 준비하는 과정 | 화면 파일과 Docker 이미지 만들기 |
| 로그 | 실행 중 남긴 기록 | 실행 실패 이유 확인 |

## Docker에 나오는 말

| 단어 | 쉬운 뜻 |
| --- | --- |
| Docker | 필요한 프로그램과 실행 환경을 묶어 실행하는 도구 |
| 이미지 | 프로그램과 실행 환경이 들어 있는 준비 묶음 |
| 컨테이너 | 그 이미지를 사용해 실제로 실행하는 단위 |
| Dockerfile | 이미지를 어떻게 만들지 적은 설명서 |
| Compose | 여러 컨테이너를 함께 켜고 끄는 기능 |
| 서비스 | Compose에서 정한 실행 대상 이름. 여기서는 `frontend`, `backend`, `db` |
| 볼륨 | 컨테이너를 다시 만들어도 데이터를 남겨 두는 저장 공간 |
| Nginx | 화면 파일을 보내고 서버로 갈 요청을 전달하는 프로그램 |

## Git과 GitHub에 나오는 말

| 단어 | 쉬운 뜻 |
| --- | --- |
| Git | 파일이 어떻게 바뀌었는지 이력을 기록하는 도구 |
| GitHub | Git 이력을 인터넷에 올려 함께 사용하는 서비스 |
| 저장소, Repository | 프로젝트 파일과 변경 이력을 모아 둔 곳 |
| 브랜치, Branch | 공용 코드에서 갈라져 내 작업을 따로 기록하는 공간 |
| main | 두 사람이 합의한 공용 코드가 들어가는 브랜치 이름 |
| origin | 내 PC에 등록해 둔 GitHub 저장소의 별명 |
| origin/main | 마지막으로 받아 확인한 GitHub main의 위치 |
| Commit, 커밋 | 지금 변경을 내 PC의 Git 이력에 기록하기 |
| Push, 푸시 | 내 커밋을 GitHub에 올리기 |
| Fetch | GitHub의 최신 이력 정보만 받기. 작업 파일은 그대로 |
| Pull | GitHub 이력을 받아 현재 브랜치에 반영하기 |
| PR, Pull Request | 내 변경을 공용 코드에 합쳐 달라는 검토 요청 |
| 리뷰, Review | 상대방이 변경 내용을 살펴보는 과정 |
| Approve, 승인 | 검토 후 합쳐도 좋다고 표시하기 |
| Merge, 병합 | 두 갈래의 변경을 실제로 합치기 |
| 충돌, Conflict | Git이 자동으로 합칠 결과를 결정하지 못한 상태 |
| Squash and merge | PR의 여러 기록을 하나로 묶어 공용 코드에 합치기 |
| CI | 코드를 올릴 때 정해진 검사를 자동으로 실행하는 방식 |
| GitHub Actions | GitHub에서 자동 검사 등을 실행하는 기능 |
| Ruleset | GitHub에서 병합 조건 등을 정하는 보호 설정 |

**파일 저장 → Commit → Push → PR → 승인 → Merge는 각각 다른 단계입니다.** 특히 승인만으로 공용 코드에 합쳐진 것은 아닙니다.
