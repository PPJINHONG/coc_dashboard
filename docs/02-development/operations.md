# 운영 데이터 설계

[문서 목록](../README.md) · [데이터 확인과 DB 구조 변경](database.md) · [관리자 DB 관리](database-admin.md)

인프라 자원·운영 작업은 **기준 월별로** 저장합니다. 권역별 요청작업은 서버가 기록한 KST 요청일이 속한 월로 자동 분류합니다. 운영 인력과 공통데이터(리전·서비스·인력)는 월 구분 없이 현재값 하나입니다. K8s 기능과 주별 테이블은 없습니다.

### 기준 월

- 열: 각 월별 테이블의 `period_month`(DATE, 그 달 1일만 허용. 검사 제약 `*_month_first_day`). 기본값은 이번 달(Asia/Seoul).
- API: `month`를 `YYYY-MM`으로 주고받습니다. 조회는 `?month=2026-08`, 저장은 본문 `"month": "2026-08"`. 없으면 이번 달이고 형식이 틀리면 `400`입니다. 응답의 각 행과 최상위에 `month`가 있습니다.
- 인프라 자원·운영 작업은 월마다 따로 입력합니다. 새 달은 빈 상태로 시작하며 지난달 값을 자동 복사하지 않습니다.
- 권역별 요청작업의 `period_month`는 사용자가 고르지 않습니다. 서버가 요청 등록 시각을 KST로 환산해 해당 월 1일을 저장하고, 목록은 `?month=YYYY-MM`으로 구분합니다.
- 합계(`totals`)는 조회한 월 기준입니다. 운영 인력 수는 월과 관계없이 전체입니다.
- 마이그레이션 적용 전에 있던 행은 2026-11월로 들어갔습니다.
- 화면: 상단바의 기준 월 선택(이전 달·목록·다음 달, 이번 달부터 24개월 전까지)이 모든 탭과 DB 관리에 같이 적용됩니다. 처음 열면 이번 달이고, 편집 중에 월을 바꾸면 확인 창을 띄웁니다. 코드는 `frontend/src/app/AppShell.tsx`(`MonthPicker`)이며 저장 요청은 `snapshot.month`를 보냅니다.

리전·서비스·인력은 **공통데이터**입니다. 모든 기능이 같은 원본을 참조하며 자동으로 만들지 않습니다. 관리자가 DB 관리 → 공통데이터에서 등록합니다. 공통데이터에는 사용 상태(`is_active`) 열이 없습니다. `auth_user.is_active`(로그인 가능 여부)와 업무 진행 상태는 별개입니다.

- 리전과 인력은 자동 생성되는 숫자 ID로 연결합니다. 화면에서는 이름으로 고르고 ID는 DB 원본에서만 보입니다. 서비스 코드와 국가 코드는 직접 입력하는 값입니다.
- 리전 기본 목록은 이름순, 인프라 요약 그래프는 수량 내림차순입니다.
- `ops_regions.global_region`(전체 리전)은 `country_code`로 DB가 계산하는 생성 열입니다. KR·CN=내수, EU=유럽, NA=북미, 그 외 NULL. 아직 화면·API에서 쓰지 않습니다. 분류를 바꾸려면 모델·마이그레이션의 계산식을 함께 바꿉니다.
- 인프라 고유 조합은 기준 월·리전·서비스(`unique_monthly_resource_service`), 운영 작업은 기준 월·리전·작업유형·범위(`unique_monthly_work_scope`)입니다. VM·Compute Rack·Storage Rack의 빈 값은 미입력, 0은 실제 0개입니다. 상단 Rack 카드는 Compute + Storage 합계이며 둘 다 비어 있을 때만 미입력입니다.
- 운영 인력은 리전 대신 국가 코드(KR·EU·NA)를 저장하며 API와 DB가 허용값을 검사합니다.

### 운영 인력 등록·수정

- 운영 인력은 운영 인력 탭에서 표로 조회하고, 등록·수정은 사람별 팝업을 사용합니다. DB 관리 > 기능별 설정에서는 운영 인력을 제외하며 행 추가·복사·삭제 UI는 제공하지 않습니다.
- `POST /api/operations/staff/`는 등록, `PATCH /api/operations/staff/`는 한 사람의 수정입니다. 본문은 `{revision, person}`이며 수정 시 `person.id`가 필요합니다. 다른 인력은 변경·삭제하지 않으며 변경 이력과 행동 이력을 남깁니다.
- 권역은 한국(KR)·미국(NA)·유럽(EU)입니다. 소속사·근무지는 등록된 선택지에서 고르며, 근무지는 권역별로 관리합니다. 관리자·팀장만 운영 인력 탭의 선택지 관리에서 추가·삭제합니다. 선택지가 없는 항목은 미등록으로 시작하고 기존 인력의 값은 옵션 삭제 후에도 그대로 보존합니다. 직책·권역·등급은 각 권한·검증 규칙을 따르는 고정 목록입니다.
- 직책 선택은 책임 → 그룹장 → 팀장 → 관리자 순서입니다. 로그인 계정의 권한보다 높은 직책을 지정하거나 상위 직책 인력을 수정할 수 없습니다. 그룹장은 관리 국가만, 팀장·관리자는 전체 국가를 관리합니다. 기존 자유 입력 직책은 보존하며 일반 직책 수준으로 취급합니다.
- 표시 직책과 L1~L4 등급을 바꿔도 로그인 계정의 권한은 바뀌지 않습니다. 관리자·팀장이 운영 인력 수정 팝업의 `회원 계정 연결`에서 활성 계정을 연결합니다. 계정 하나는 인력 한 명에만 연결하며 동명이인을 이름으로 자동 연결하지 않습니다. 연결된 회원은 본인의 성명·업무·근무지·IP·접속 계정 정보를 수정할 수 있고, 권역·직책·소속사·투입일·회사 퇴사일·등급·계정 연결은 변경할 수 없습니다.
- `deployment_date`는 운영 업무 투입일, `resignation_date`는 회사 퇴사일(마지막 재직일)입니다. 그룹장 이상만 관리 범위에서 변경하며 퇴사일이 투입일보다 빠르면 거절합니다. 재직 상태는 권역 현지 날짜와 회사 퇴사일로 계산하고, 휴가 중인 사람도 재직중으로 표시합니다. 소속 권역의 도메인(KR=내수·NA=북미·EU=유럽)은 국가 코드에서 계산합니다.
- `grade`는 미등록 또는 L1~L4입니다. 실제 활성 관리자·팀장만 조회·수정하며 등급 값 자체는 권한 판정에 사용하지 않습니다. 다른 역할에는 현재값·CSV·변경 이력에서 등급을 제공하지 않습니다. 기능별 registry의 `Section.private_fields`를 이용해 복구용 원본에서도 권한 없는 사용자의 응답을 정제합니다.
- 회원을 연결하면 회원 성명을 운영 인력 공통데이터와 공유합니다. 이후 회원정보나 운영 인력에서 이름을 수정하면 양쪽에 반영되며, 연결된 성명은 인력 공통데이터 기준인 100자 이하로 제한합니다. 이름만으로 계정을 추측해 연결하지 않습니다.
- 도메인·소속사·직책·재직/휴가 상태·등급(열람 권한자만)·투입일/퇴사일 기간 필터와 표시 컬럼 선택을 제공합니다. CSV에는 적용된 필터와 표시 컬럼을 사용합니다. 운영 인력 탭의 `인력 목록 / 캘린더 / 인력 추이`는 같은 인력을 참조합니다.
- `ops_staff_responsibilities`에서 권역별 현장대리인·팀장·그룹장을 인력으로 연결합니다. 그룹장은 관리 권역, 관리자·팀장은 전체 권역을 설정합니다. 현장대리인·그룹장은 해당 권역의 인력만 지정하며 팀장은 전체 인력에서 지정할 수 있습니다. 이름·초기 업무 데이터는 마이그레이션이나 시작 과정에서 자동 등록하지 않습니다.

### 인력 캘린더·추이

- 휴가·결혼휴가·장기휴가는 `ops_staff_calendar_events`의 시작일·종료일(포함)·선택 제목으로 저장합니다. 승인 없이 즉시 반영되며 목록의 현재 상태는 오늘의 일정을 계산합니다. KR은 Asia/Seoul, NA는 America/Los_Angeles, EU는 Europe/Berlin의 현지 날짜를 사용합니다.
- 모든 로그인 사용자가 전체 합친 캘린더 및 KR·EU·NA별 캘린더를 조회합니다. 활성 계정과 연결된 본인만 일정 등록·수정·삭제가 가능하며 관리자·팀장·그룹장도 타인의 일정을 변경할 수 없습니다. 옵저버는 조회만 가능합니다. 기간 역전·중복·업무 투입 전·회사 퇴사 후 일정은 거절합니다. 연결 없는 인력은 관리자·팀장의 계정 연결 후 본인 일정 등록을 사용합니다.
- 캘린더의 권역 필터는 인력의 현재 소속 권역을 따릅니다. 권역을 바꾸면 현재 캘린더 조회도 새 권역으로 이동하고, 이전 권역의 현장대리인·그룹장 지정은 해제합니다. 이전 일정 등록 당시의 권역은 변경 이력 원본에 보존합니다.
- `GET/POST operations/staff/calendar/`, `PATCH/DELETE operations/staff/calendar/{id}/`를 사용합니다. 조회는 `month=YYYY-MM`, 선택 `country=KR|EU|NA`를 받으며 해당 월과 겹치는 여러 날 일정을 포함합니다. 저장은 `{revision, event}`, 삭제는 `{revision}`입니다. 서버가 소유 인력과 권역을 결정하며 다른 인력을 지정할 수 없습니다.
- `GET operations/staff/options/`는 본인 인력 연결 여부·일정 수정 여부·등급 열람 여부·권역 책임자를 제공합니다. 회원 연결 선택지는 관리자·팀장에게만 제공합니다. `PUT operations/staff/responsibilities/`는 `{revision, responsibility}`로 책임자를 저장합니다.
- `GET/POST operations/staff/choices/`, `DELETE operations/staff/choices/{id}/`는 소속사·권역별 근무지 선택지를 다룹니다. 활성 로그인 사용자는 조회하고 관리자·팀장만 `{revision, choice}`로 추가하거나 `{revision}`으로 삭제합니다. 중복·빈 값·길이·권역을 검사하며, 옵션 삭제는 인력 데이터를 바꾸지 않습니다. 추가·삭제는 변경·행동 이력과 관리자 복구에 포함합니다. 기존 인력 저장 API의 문자열 형식은 유지합니다.
- `GET operations/staff/trend/?month=YYYY-MM&country=&company=`는 최근 12개월 투입·회사 퇴사·순증감·운영 인원을 실제 날짜로 집계합니다. 과거 월은 월말, 현재 월은 오늘의 종료 시점 기준이며 회사 퇴사일의 종료 시점부터 제외합니다. 현재 권역·소속사 기준 분류임을 표시하며 투입일 미등록 인력은 임의 날짜를 넣지 않고 제외 건수를 표시합니다.
- 캘린더와 책임자 변경도 운영 인력의 변경·행동 이력에 남기며 복구용 모델은 운영 인력 `feature.py`에 등록합니다. 인력 삭제로 일정이 함께 사라지지 않도록 연결된 일정은 PROTECT로 보존합니다.

### 회원정보

- 사이드바 관리 메뉴의 `회원정보`(`members`)에서 실제 가입 계정을 조회·추가·수정합니다. 관리자·팀장만 접근하며 기존 DB 관리 > 기능별 설정의 사용자·권한은 제거합니다.
- 이름·이메일 아이디 검색과 역할·관리 권역·활성 상태 필터, 회원 정보·역할 및 권한 팝업을 제공합니다. 목록의 수정 가능 여부와 지정 가능한 역할은 서버가 계산합니다.
- 관리자는 팀장·그룹장·사용자·옵저버를, 팀장은 그룹장·사용자·옵저버를 관리합니다. 본인과 동급·상위 역할은 조회만 하며 직접 API를 호출해도 변경할 수 없습니다. `is_staff` 직접 지정에도 같은 제한을 적용합니다. 표시 이름 `책임 (사용자)`는 기존 `user` 역할입니다.
- `GET/POST /api/members/`, `PATCH /api/members/{id}/`를 사용합니다. 회원 추가는 실제 로그인 계정을 생성하며 운영 인력 데이터와 자동 연결하지 않습니다. 신규 비밀번호와 비밀번호 변경은 기존 검증을 사용하고 원문·해시를 응답과 이력에 넣지 않습니다.
- 그룹장은 관리 권역을 하나 이상 지정하며 다른 역할로 바꾸면 관리 권역을 해제합니다. 비활성 계정은 로그인할 수 없습니다. 새 탭은 비활성화로 계정 상태를 관리하며 실제 계정 삭제 UI는 제공하지 않습니다.
- 회원정보의 별도 이력 버튼·팝업은 제거하고 계정 등록·수정·삭제·역할 변경은 변경 이력 탭의 회원정보에서 확인합니다. 행동 이력도 유지하며 비밀번호 값은 기록하지 않습니다. 관리자·팀장의 관리 권역은 `ALL`로 표시합니다. 과거 `/api/db-admin/accounts/` API는 동일한 하위 역할 제한을 적용해 호환 유지합니다.
- 기존 `PUT` 일괄 API는 호환을 위해 유지하되 상위 직책 인력은 일괄 수정·삭제 범위에서 제외합니다.

## 2. API와 저장

| 경로 (`/api/` 아래) | 방식 | 내용 | 코드 |
| --- | --- | --- | --- |
| `operations/bootstrap/` | GET | 공통데이터·관리자 여부 | `reporting/views.py` |
| `operations/current/[?month=YYYY-MM]` | GET | 기준 월의 기능별 데이터·합계·버전·권한 범위의 최근 변경 이력 50건 | `reporting/views.py` + 각 `feature.py` |
| `operations/logs/[?section=&month=&region=&actor=&offset=]` | GET | 권한 범위의 변경 이력, 최신순 30건씩·기능별 최근 변경순·필터 목록 | `reporting/views.py`, `reporting/history.py` |
| `db-admin/logs/{id}/restore-preview/`, `restore/` | POST | 관리자 복구 가능 여부 확인·최종 확인 후 복구 | `reporting/restoration.py` |
| `operations/regional_requests/[?month=&region=]` | GET/POST | 월·리전별 요청 목록 조회와 요청 등록 | `features/regional_requests/views.py` |
| `db-admin/sections/{기능}/` | PUT | `{revision, month, rows}`로 기준 월 데이터 전체 저장(관리자) | `reporting/views.py` |
| `db-admin/common/{regions·services·staff-members}/[{pk}/]` | POST/PATCH/DELETE | 공통데이터 관리(관리자) | `reporting/views.py` |

`{기능}`은 각 기능 앱 `feature.py`의 `Section.key`(`resources`, `staff`, `work`)입니다.

- 일반 기능 화면은 기본적으로 조회 전용입니다. 업무 데이터와 공통데이터의 일괄 변경은 `/api/db-admin/`에서 **실제 활성 관리자만** 합니다. 개발용 로그인 우회(`DEVELOPMENT_AUTH_BYPASS`)도 쓰기 권한을 주지 않습니다.
- 예외: 권역별 요청작업은 일반 화면에서 관리자와 사용자가 등록합니다. 요청 리전은 KR·NA·EU 중 하나입니다. 요청 내용은 작성자·관리자만 수정하고 상태·담당 권역·자유 입력 담당자는 관리자·사용자가 수정하며 삭제는 관리자만 합니다.
- 기능별 저장은 기준 월의 전체 행을 보냅니다(월별 기능). 기존 행은 `id`를 유지하고 새 행은 생략합니다. 다른 달의 `id`는 거절합니다. 그 월에서 빠진 행만 실제로 삭제하고 다른 달 행은 그대로 둡니다. 연결된 데이터(댓글, 사용 중인 공통데이터)가 있으면 거절합니다.
- 모든 저장은 `revision`을 확인합니다. 다른 저장이 먼저 있었으면 `409`이며 최신 데이터를 다시 불러와 편집합니다. 수량·상태 제약은 서버와 DB가 함께 검사합니다(오류 `400`).
- 열 이름이 바뀐 뒤 예전 열 이름(`environment_name`, `zone_name` 등)으로 보내는 요청은 거절해 오래 열린 화면이 값을 바꾸지 않게 합니다.

## 3. 권한

| 권한 | 저장 방법 | 할 수 있는 일 |
| --- | --- | --- |
| 관리자 | `is_staff=true` | 모든 조회·수정·삭제, DB 관리, 변경 이력·행동 이력 |
| 팀장 | `team_lead` 그룹 | 사용자 권한 + 운영 인력 탭에서 전체 국가 운영 인력 편집 |
| 그룹장 | `group_lead_KR`·`_EU`·`_NA` 그룹 | 사용자 권한 + 관리 국가의 운영 인력만 편집(국가도 관리 국가로만 선택) |
| 옵저버 | `observer` 그룹 | 조회만. 모든 쓰기·초대 발급·취소는 `403` |
| 사용자 | 그 외 활성 계정 | 조회, 권역별 요청작업 등록, 모든 요청의 상태·담당 변경, 본인 요청 내용 수정, 초대 발급 |

- 권역별 요청작업 응답은 `can_edit_content`, `can_update_assignment`, `can_delete`를 내려 주고 화면은 이 값으로만 버튼을 보여 줍니다. 작성자 아이디는 응답에 넣지 않습니다.
- 권역별 요청작업 삭제는 관리자만 가능하며, 옵저버는 조회만 합니다.
- 권한 변경은 관리자·팀장이 회원정보 메뉴에서 하위 역할에만 수행합니다. 기존 관리자 계정 API에도 같은 제한을 적용하며 `/api/me/`는 조회 전용입니다.

### 변경 이력 조회와 복구

- 변경 이력은 일반 기능 메뉴에서 조회합니다. 사용자·옵저버는 본인이 변경한 이력, 그룹장은 관리 국가의 변경 항목만, 팀장·관리자는 전체를 봅니다. 일괄 저장에 여러 국가가 섞여 있어도 그룹장에게 다른 국가의 변경 전후 원본·필터 항목은 노출하지 않습니다. 작성자 아이디도 응답에서 제거합니다.
- 기능 선택 목록은 최근 변경이 있는 기능부터, 각 기능의 이력은 최신순입니다. 화면의 목록·탭에는 건수를 표시하지 않습니다. 리전·사용자·기준 월을 함께 선택하며 기본은 전체 기간입니다. API는 페이지 이동을 위한 `results`, `count`, `next_offset`, `tabs`, `actors`, `regions`를 반환합니다. `actor`는 응답의 불투명한 사용자 키, `region`은 공통 리전 ID 또는 요청작업의 KR·NA·EU 권역 코드입니다.
- 새 이력은 변경 전후의 실제 원본을 `restore_data`에 보존합니다. 현재값 기능은 `Section.history_models`에 관련 모델을 부모→자식 순서로 등록합니다. 별도 작성 API인 요청작업은 `Feature.histories`의 `History`에 모델과 권역 해석 함수를 등록하며 관리자 일괄 저장 경로에는 등록하지 않습니다. 운영 인력 이름·배치·캘린더·책임자·선택지 및 요청작업·이미지의 실제 변경 행만 보존합니다. 데이터 변경 전에 전역 버전 잠금을 얻고 `capture_history`를 호출한 뒤 기존 `record_log`로 기록합니다.
- 요청작업의 원본 이미지는 기존 파일 삭제 신호가 실행되기 전에 미디어 볼륨의 `history_backups/`에 내용 해시와 함께 보관합니다. 삭제·본문 이미지 제거를 복구하면 이미지 행과 파일을 함께 복원하며 파일 누락·내용 충돌 시 전체 DB 복구를 취소합니다. 요청 등록을 되돌릴 때는 첨부를 먼저 업로드 초안으로 분리하여 CASCADE로 함께 삭제되지 않게 합니다. 기존 이슈·댓글 데이터는 사용자 승인과 백업 후 삭제 마이그레이션을 적용하며, 제거된 기능의 이력은 현재 변경 이력 목록에서 제외합니다.
- 관리자는 오른쪽 복구 버튼에서 변경 대상 확인 → 최종 확인을 거칩니다. 서버는 사용자·이력·버전에 묶인 5분 유효 서명 토큰, CSRF, 관리자 권한, 현재 원본 일치 여부를 검사합니다. 변경된 행만 되돌리므로 다른 월·다른 행의 이후 변경은 유지됩니다. 이후 같은 행의 값이 바뀌었거나 연결 데이터·제약과 충돌하면 전체 작업을 취소합니다.
- 복구 성공은 새로운 변경 이력(`action=restore`, `restored_from`)과 행동 이력으로 남습니다. 같은 이력의 중복 복구와 복구 기록 자체의 복구는 금지합니다. 복구 원본이 없는 과거 이력은 조회만 지원하며 화면에 사유를 표시합니다. 기능별 스냅샷을 얻기 위해 해당 기능과 관련 모델을 조회하므로 대규모 데이터로 확장할 때는 변경 대상만 수집하는 방식을 검토합니다.

## 4. 개인 화면 설정

`GET/PATCH /api/navigation/preferences/`는 본인의 `hidden_tabs`, `sidebar_collapsed`만 다룹니다. 로그인 사용자는 계정별, 비로그인 개발 화면은 서명된 HttpOnly 쿠키로 브라우저별로 저장합니다. 처음 로그인하면 브라우저 설정을 계정으로 가져옵니다. PATCH에는 CSRF가 필요합니다. 숨길 수 있는 탭은 각 앱 `feature.py`의 `tabs`이며 홈·DB 관리는 숨길 수 없습니다. 업무 데이터 권한과는 별개입니다.
