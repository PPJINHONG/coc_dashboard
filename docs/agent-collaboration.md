# 에이전트 협업

사용자 담당 구성은 **총괄 → 기능 구현 → 검증·완료 보고**의 세 에이전트이다. 프론트·백엔드 전담 구성을 대체하며, CI·Git은 별도 담당 영역으로 유지한다. 공통 규칙은 루트 `AGENTS.md`, 역할 정의는 `.codex/agents/*.toml`에서 관리한다.

## 역할과 수정 범위

| 역할 | 이름 | 책임 | 수정 범위 |
| --- | --- | --- | --- |
| 총괄 | `project_manager` | 사용자 지시 접수, 요구사항·수용 기준 정리, 범위 배정, 수정·재검증 조율, 검증 보고 전달 | 에이전트 설정·공통 문서·설정 등 업무별로 정한 파일. CI·Git 영역은 별도 담당자와 조율 |
| 기능 구현 | `feature_implementer` | 기능의 화면·API·DB 연동과 문서 구현, 자체 검사, 수정 요청 처리 | 총괄이 배정한 `frontend/`, `backend/`, `db/`, `docs/`, 공통 설정의 구체적인 파일·경로 |
| 검증 | `verifier` | 사용자 원문과 수용 기준 대조, 실제 기능과 관련 기존 동작 확인, 판정·검증 보고서 작성 | 제품 코드·설정·요구사항은 수정하지 않음. 배정된 임시 경로의 검증 산출물·보고서만 작성 가능 |

기능 구현자는 양쪽 폴더를 수정할 수 있지만 프로젝트 전체를 자유롭게 변경하지 않는다. 총괄이 먼저 변경 허용 범위와 보호할 기존 동작을 정하며, 범위 밖 수정이 필요하면 사유와 영향을 전달해 배정을 갱신한다.

역할 지침은 파일 쓰기를 강제 차단하는 보안 경계가 아니다. 사용자 정의 역할의 모델·권한은 별도로 고정하지 않고 부모 세션 설정을 따른다. 검증의 읽기 중심 원칙도 역할 지침이며 운영체제 수준의 읽기 전용 권한을 설정했다는 의미는 아니다.

## 실행 흐름

1. **지시 접수:** 총괄이 사용자 원문, 현재 브랜치·기존 변경, 관련 구현·문서를 확인한다. 요구사항에 `R1`, `R2`처럼 식별자를 붙이고 항목별 수용 기준을 작성한다. 필요한 결정만 사용자에게 확인하고 요구사항을 임의로 줄이지 않는다.
2. **구현 배정:** 총괄이 원문, 수용 기준, 수정 허용 경로, 보호할 기존 동작, API 계약, 실행 환경과 검증 시나리오를 기능 구현자에게 전달한다. 미합의 정책이 필요한 부분은 결정 후 진행한다.
3. **기능 구현:** 구현자가 배정된 범위에서 기능과 관련 문서를 수정하고 자체 검사를 수행한다. 변경 파일, 실행 명령·결과, 기존 기능에 대한 영향, 남은 문제를 인계한다. 자체 검사 통과는 최종 완료 판정이 아니다.
4. **대상 고정:** 총괄이 검증할 브랜치·커밋 또는 미커밋 변경 목록과 파일 상태를 명시한다. 검증하는 동안 해당 코드의 편집을 멈추고 구현자의 자체 검사 결과도 전달한다.
5. **독립 검증:** 검증자가 구현자의 설명 외에 사용자 원문·수용 기준·실제 변경을 직접 대조한다. 변경에 맞는 화면 조작, HTTP/API 호출, DB 결과 확인과 관련 기존 동작 확인을 수행한다. 빌드만으로 화면·API·DB 검증을 대체하지 않는다.
6. **수정과 재검증:** `FAIL`은 기대값·실제값·재현 절차와 함께 총괄 및 구현자에게 돌려보낸다. 총괄이 수정 범위를 정하고 구현자가 수정한 뒤, 새 대상 상태에서 실패 항목과 변경 영향 범위를 다시 검증한다. 검증자가 제품 코드를 직접 고쳐 통과시키지 않는다.
7. **검증 보고:** 검증자가 요구사항별 판정·근거·관련 기존 기능 결과·남은 문제를 작성한다. 총괄이 이 결과를 사용자에게 전달한다. 필수 기준이 모두 `PASS`이고 실제 기능 동작 근거가 있을 때 완료로 보고한다.

이 흐름은 순차적으로 수행한다. 구현과 해당 결과의 검증을 동시에 실행하지 않는다. 코드가 검증 이후 다시 바뀌면 영향받는 기준을 재검증하기 전에는 기존 판정을 그대로 사용하지 않는다. 런타임에 역할이 노출되지 않으면 동일 지침을 전달한 별도 에이전트를 사용하고, 독립 검증을 수행하지 못했다면 이를 보고한다.

## 판정과 실제 동작 확인

| 판정 | 의미 | 처리 |
| --- | --- | --- |
| `PASS` | 해당 요구사항의 기대 결과를 실제 검사로 확인 | 근거와 검증 대상 상태 기록 |
| `FAIL` | 요구사항 불일치, 기능 실패 또는 관련 기존 동작의 퇴행 확인 | 재현 절차와 함께 구현으로 반환 |
| `NOT_VERIFIED` | 환경·접근·도구 부족 등으로 실제 확인하지 못함 | 이유와 필요한 조건 기록. 완료 판정 보류 |

검증은 변경과 관련된 범위에서 수행한다. 사용자 요구사항별 정상 동작과 필요한 오류·빈 결과 등 경계 상황을 확인하고, 공통 컴포넌트·API·DB처럼 영향을 받는 기존 동작도 포함한다. 정적 코드 검토, 타입 검사, 빌드, 실제 기능 실행 결과는 각각 구분한다. UI 기능은 화면 검증 없이 API 성공만으로 통과시키지 않는다.

검증 명령은 빌드 파일·캐시·테스트 데이터를 생성할 수 있다. 허용된 환경·산출물 경로·테스트 데이터 범위를 배정에 명시하고 기존 사용자 데이터 변경, DB 초기화·볼륨 삭제로 검증 환경을 맞추지 않는다. 제품 소스·설정·수용 기준을 변경할 필요가 있으면 총괄과 구현자에게 반환한다. 실제 비밀값은 출력하거나 보고서에 담지 않는다.

## 배정·인계 양식

총괄 → 기능 구현 및 검증:

```text
작업 목표 / 사용자 원문:
요구사항과 수용 기준: R1 ..., R2 ...
수정 허용 파일·경로:
보호할 기존 동작 / API 계약:
선행 합의 / 미정 사항:
검증 환경 / 허용 산출물·테스트 데이터:
요구사항별 검증 시나리오와 기대 결과:
```

기능 구현 → 총괄 및 검증:

```text
변경 목적 / 요구사항별 구현 내용:
변경 파일 / 기존 변경과의 구분:
자체 검사 명령과 결과:
다른 영역과 기존 기능에 미치는 영향:
실행 방법 / 남은 문제:
```

검증 → 총괄 → 사용자:

```text
검증 대상: 브랜치·커밋 또는 미커밋 파일 상태
검증 환경:
요구사항별 판정: R1 PASS/FAIL/NOT_VERIFIED — 명령·절차, 기대값, 실제값
관련 기존 동작 확인 결과:
실패 재현 절차 / 미검증 이유:
최종 판정: 완료 / 수정 필요 / 검증 미완료
남은 문제 / 다음 작업:
```

보고서는 대화로 전달할 수 있다. 파일로 남겨야 하면 총괄이 작성 경로를 지정하고 공유 문서를 여러 에이전트가 동시에 수정하지 않도록 한다.

## CI·Git과 공통 정책

- CI는 `.github/workflows/`와 `docs/github-actions.md` 등 별도 담당 영역이다. 필요한 검사·재현 명령·실패 근거와 Compose·Dockerfile 변경 영향을 총괄이 인계한다.
- Git은 브랜치·커밋·Push·PR·병합과 `.github/pull_request_template.md`, `.gitignore`, `docs/git_collaboration_guide.md` 등 별도 담당 영역이다. 총괄이 변경 파일과 검증 근거, 요청할 작업을 조율한다. 현재 브랜치 유지 지시를 따르며 같은 작업 폴더에서 편집 중 브랜치를 전환하거나 Git 쓰기를 병행하지 않는다.
- 다른 사람의 기존 변경은 보존하고 요청과 관련 없는 리팩터링·의존성 변경은 포함하지 않는다. 같은 파일은 한 명이 수정한다.
- 현재 `Basic CI`의 `Compose build`는 Compose 설정 검증과 앱 이미지 빌드를 수행한다. 프론트의 `npm run build`에는 타입 검사가 포함된다. 빌드 성공, 실제 기능 검증, 사람 리뷰를 구분한다.
- 기존 검증 도구를 사용한다. 새 테스트 도구·CI 검사, 인증·권한·쓰기 API 범위, DB 변경 관리, 운영·배포·백업 기준은 합의 여부를 확인한다. 이 역할 변경만으로 정책을 확정하지 않는다.
- 환경변수 추가 시 `.env.example`, 사용 코드/Compose, `docs/configuration.md`를 함께 갱신하고 기존 `.env`는 덮어쓰지 않는다. 설정 확인은 `docker compose config --quiet`를 사용한다.
- 규칙 변경 PR에는 폴더별 분담에서 기능 구현·독립 검증으로 바꾼 이유와 영향 범위, 이번 변경에 포함한 설정·문서를 적고 상대방의 리뷰를 받는다. 에이전트 검증은 사람 리뷰를 대체하지 않는다.

## 사용 예시

```text
project_manager 역할로 아래 업무를 받아 feature_implementer에 구현을 지시하고,
구현 후 verifier가 내 요구사항과 실제 동작을 검증하도록 진행해줘.
목표: <추가할 기능>
요구사항: <사용자가 기대하는 결과>
현재 브랜치에서 진행하고, 검증 실패 시 수정·재검증한 뒤 결과를 보고해줘.
```

프로젝트를 연 새 세션에서 세 역할의 로드 여부를 확인한다. 역할 파일 추가만으로 실행 세션이 자동 생성되지는 않는다.
